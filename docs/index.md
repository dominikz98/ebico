- [E2E: Connector ↔ Server (happy paths)](development/e2e-connector-server.md) — the first **real round-trip** between `EBICO.Connector` and `EBICO.Server` (#57, kick-off of M8): until now each side was only tested against a **model** of the other (tier-A fakes in the connector, hand-built request XML in the server), so a consistently-wrong wire-format assumption was invisible; now the real connector pipeline talks over `WebApplicationFactory<Program>` + `ConfigurePrimaryHttpMessageHandler(() => factory.Server.CreateHandler())` against the real server pipeline (the real `HttpClientTransport` stays in play — **pitfall:** it posts against the *absolute* `EbicsConnection.Url`, not the `BaseAddress`); covered per **H003/H004/H005**: **INI/HIA/HPB** (real `ISubscriberKeyGenerator`, real state transition `New → Initialized → Ready`, `HpbResult.FingerprintsVerified` as evidence that the loop compress→E002→wire→decrypt closes), **upload CCT** (server-side recovery of the pain.001 bytes; `EffectiveOrderType == "CCT"` checks the seam that no single layer sees — H003/H004 `OrderType` directly vs. H005 `BTU`+BTF) and **download C53** (camt.053-in-ZIP, three-phase incl. receipt → **`011000`**, *not* `000000`); `EbicsE2EHarness` + `E2EKeyPool` (RSA-2048 is a hard lower bound in `RsaKeyMaterial` ⇒ key reuse instead of smaller keys), isolation per test via its own `HostID` instead of its own host, subscribers deliberately seeded in state `New`; three seam-specific negative cases (order `091002`, authorisation `090003`, invalid pain.001 `090004`); spec caveats (X002 is generated, but checked in **neither** direction — `NoOpEbicsRequestVerifier` + unsigned response, M4; ES/A00x unchecked; synthetic C53 data; the counterpart is the emulator, not a real client → #59)
- [E2E: negative & security cases](development/negative-security-cases.md) — the **security/negative tier** of M8 (#58, builds on #57): switches the **server-side X002 authentication-signature verification** into production (`X002EbicsRequestVerifier` replaces `NoOpEbicsRequestVerifier`; verifies every signed `ebicsRequest` against the auth key stored in the `IServerKeyStore`, only after HIA — subscriber via header or transaction store, failure → `061001` `EBICS_AUTHENTICATION_FAILED`) and proves it end-to-end via a **wire-tampering negative suite** (`RequestTamperingHandler` in the E2E harness, armed after onboarding): tampered `SignatureValue` or tampered authenticated header (`NumSegments`) → **`061001`** (the whole `EbicsRequestHeader` is `authenticate="true"`, so X002 protects the segment metadata), tampered — **not** authenticated — `OrderData` → **`090004`** `EBICS_INVALID_ORDER_DATA_FORMAT` (survives the signature, fails on decryption), per H003/H004/H005; the classic segment-inconsistency codes (`091103`/`011101`/`091104`/`091101`) remain covered at the server-pipeline level (a validly signed but inconsistent request only arises there); spec caveats (expired keys unchecked server-side — no validity window stored, M3/M4; ES/A00x unchecked; server responses unsigned), ADR-0023
- [Conformance against real clients](development/conformance-real-clients.md) — the **foreign-client closure** of M8 (#59, closes epic #56): a new test tier `tests/EBICO.Tests/Conformance/` checks EBICO against **real, foreign EBICS clients** instead of only against its own counterpart — with **committed vendor captures** of a real OSS client (`ebics-client`/node-ebics-client, MIT, H004; produced once locally via `tools/vendor-capture/`, the output of an OSS client is committable — unlike proprietary ebics.org samples, ADR-0026), **parser/wire-shape tolerance** (`XmlShape`: namespace prefix instead of default incl. `xsi:type` rewrite, whitespace, comments on EBICO's own XML), **C14N algorithm adaptivity** (X002 verification with inclusive **and** exclusive C14N, `C14nAlgorithms.FromAlgorithmUri`) and **known-gap negative cases** (H005 `RSAKeyValue` instead of certificate, uncompressed order data → each `090004`); the vendor replay immediately found the **central interop deviation** that EBICO↔EBICO tests hide by construction: EBICO's generated binding typed `OrderDetails` **abstract** and demanded an `xsi:type` discriminator that its own connector emitted but a real client omits → **all** onboarding requests of the real client were rejected (wrongly as `061099`, i.e. a server rather than client error) — **fixed with #117** (ADR-0029), together with two defects only visible behind it (`A006`/PSS on H004, `ds:Modulus` with ASN.1 sign byte → 2056-bit import); the replay has thereby turned from a characterisation test into a **conformance test** and drives the chain INI → HIA → HPB of a real client through to `SubscriberState.Ready`; plus a **compatibility matrix**, a **deviation** section (fixed findings + consolidated spec caveats) with an honesty boundary (wire-shape/C14N are self-consistency; even the vendor replay checks no **foreign signature**, since the X002 verifier skips HPB) and a **doc guard** (`ConformanceMatrixTests`); tier-B XSD validation skip-if-missing, ADR-0026/ADR-0029

## Server (emulator)

- [Hostable server skeleton (ASP.NET Core)](server/host.md) — EBICS HTTP endpoint (POST, `text/xml`), request pipeline (parse → version dispatch → verify → handle → respond) with verify/handle as extension points, central error mapping to EBICS return codes, pluggable in-memory state store (`AddEbicoServer`)
- [Master-data management (banks/partner/subscriber)](server/master-data.md) — CRUD in the server state, referential integrity & cascading deletion, authorisations per OrderType/BTF, multi-bank/multi-tenant capability, unauthenticated HTTP admin API (`MapEbicoAdminApi`)
- [BTF framework (H005)](server/btf-framework.md) — typed **Business-Transaction-Format** model (`EBICO.Core.Btf`: Service/Option/Scope/Container/MsgName/Version/Format), mapping **BTF ↔ classic OrderTypes** (`BtfOrderTypeCatalog`, representative best-effort seed after the EBICS BTF mapping list), **strict authorisation check per BTF** in the upload/download init (`Subscriber.HasPermissionFor` → `090003` EBICS_AUTHORISATION_ORDER_TYPE_FAILED), extraction of the BTF service from `BTUOrderParams`/`BTDOrderParams`; foundation for the concrete orders (#39–#43), ADR-0016; spec caveats (External Code List proprietary, `FUL`/`FDL` `FileFormat`→BTF & `SignatureFlag` deferred)
- [Upload orders: payments (CCT/CDD/CDB/CIP)](server/payment-orders.md) — the first **business order processing** on the upload transaction (#39): structural validation of the SEPA pain payloads (`EBICO.Core.Payments.SepaPaymentValidator`, `pain.001` for CCT/CIP, `pain.008` for CDD/CDB — namespace/mandatory fields/`NbOfTxs`+`CtrlSum` cross-checks, **no** XSD) and **storage of a pain.002 status report for later delivery** (`PainStatusReportBuilder` → `IDownloadDataProvider` under `PaymentStatusReportOrderType`, default `PSR`); pluggable `IUploadOrderProcessor` (default `SepaPaymentUploadProcessor`), resolution of all three submission conventions (H005 BTU+BTF · H003/H004 direct code · H003/H004 `FUL`+`FileFormat`) via `BtfOrderTypeCatalog.ResolveUploadOrderType`; return codes `090004` (invalid) / `090003` (unauthorised), `OrderAccepted`/`OrderRejected` events, ADR-0017; spec caveats (no XSD, ES/`SignatureFlag` still unchecked, end-to-end status-report download follows with #40)
- [Download orders: statements & reports (STA/VMK/C53/C52/C54)](server/statement-orders.md) — the **order-type-specific content generation** on the download transaction (#40): server-side **generated** synthetic statements in five formats — **STA** (SWIFT MT940), **VMK** (SWIFT MT942), **C53** (camt.053), **C52** (camt.052), **C54** (camt.054) — with a deterministic generator (`SyntheticStatementGenerator`, valid DE IBAN, running balance), **period filter** (`FDLOrderParams`/`StandardOrderParams`/`BTDOrderParams` `DateRange`) and **ZIP container** (`StatementZipContainer`, BTF `Container=Zip`); pluggable `IDownloadOrderProcessor` (default `StatementDownloadProcessor`) as a generate-on-demand fallback behind the queued data, resolution of all three conventions (H005 BTD+BTF · H003/H004 `FDL`+`FileFormat` · H003/H004 direct code) via `BtfOrderTypeCatalog.ResolveDownloadOrderType` incl. a new **VMK/mt942** catalog entry; return codes `090003`/`090005`/`091114`, ADR-0018; spec caveats (synthetic data, camt fixed at `.08`, MT-tag syntax & ZIP framing unchecked against the annex, PSR/pain.002 download open)
- [Status & protocol orders (HAC/HAA/HTD/HKD/HPD/PTK)](server/status-protocol-orders.md) — the **administrative/technical download orders** (#41): **HTD/HKD** (customer/subscriber data incl. address/accounts), **HAA** (available order types), **HPD** (bank parameters) — generated version-aware from the extended domain model (`Address`/`BankAccount`, `Partner.Address`/`Accounts`, `Bank.Url`, `Subscriber.Name`) via `SubscriberInfoContentBuilder` — as well as **HAC** (XML) / **PTK** (text) as pure **projections over [`IEventLog`](server/event-log.md)** (customer-visible, per customer) via `HacProtocolBuilder`/`PtkProtocolBuilder`; two pluggable `IDownloadOrderProcessor` (`SubscriberInfoDownloadProcessor`/`CustomerProtocolDownloadProcessor`), the engine picks from `IEnumerable<IDownloadOrderProcessor>` per `CanProcess`; **AdminOrderTypes** (no BTF), **strict authorisation** (`HasPermissionFor` → `090003`), admin API extended by address/accounts/URL/name; ADR-0019; spec caveats (HAC/PTK own projection instead of camt.086/pain.002, unmodelled binding fields, unsigned response)
- [Distributed electronic signature (HVU/HVZ/HVD/HVT/HVE/HVS)](server/veu-orders.md) — the **distributed ES** (EDS / VEU, #42): orders that need further signatures after the upload are held in a new, long-lived, partner-scoped **VEU store** (`IOpenVeuStore`/`InMemoryOpenVeuStore`, OrderID assignment); **HVU/HVZ** (overview) and **HVD/HVT** (detail per `OrderID`) are download projections (`VeuOverviewDownloadProcessor` → `VeuResponseBuilder`, version-aware), **HVE** (sign) / **HVS** (cancel) upload orders (`VeuSignatureUploadProcessor`); a complete **multi-signature workflow in the server state** — parking (trigger H005 `SignatureFlag` / H003/H004 `OrderAttribute=OZHNN`, otherwise immediate release) → signing (authorisation via `Subscriber.CanAuthorize`, E/A/B) → **release** on reaching `VeuRequiredSignatures` (default 2) with `pain.002` storage for the submitter / **cancellation**; the upload engine now takes `IEnumerable<IUploadOrderProcessor>`, new events `VeuPending`/`VeuSigned`/`VeuReleased`/`VeuCancelled`, new return code `091121` EBICS_INVALID_ORDER_IDENTIFIER; ADR-0020; spec caveats (ES unchecked, HVT order-summary, park trigger/count instead of account signature rules, unsigned response)
- [Order/BTF coverage matrix](server/order-coverage-matrix.md) — the **consolidated overall overview** of all order types modelled so far (#43, closure of M5): a family-wise matrix **OrderType/BTF × version (H003/H004/H005) × status** over key management (INI/HIA/HPB/HCA/HCS/SPR/HSA), generic carriers (FUL/FDL or BTU/BTD), payments (CCT/CIP/CDD/CDB), statements (STA/VMK/C53/C52/C54), status/protocol (HTD/HKD/HAA/HPD/HAC/PTK) and VEU orders (HVU/HVZ/HVD/HVT/HVE/HVS), with H005 BTF assignment of the business orders and a dedicated **gaps section** (Z53, PSR/pain.002 download, `SignatureFlag`, ES/X002, HEV/H3K binding-only, External Code List, conformance = M8); kept in sync with the code catalogs via a **guard test** (`OrderCoverageMatrixTests`), so that no registered OrderType silently drops out of the matrix
- [INI — sending the signature keys (A00x)](server/ini.md) — first order handler: receipt/storage of the bank-technical signature key (`IServerKeyStore`), subscriber transition `New → Initialized`, response as `ebicsKeyManagementResponse`, return codes (already initialised / broken order data), H003/H004 (`RSAKeyValue`) vs. H005 (X.509)
- [HIA — sending the auth & enc keys (X002/E002)](server/hia.md) — second order handler: receipt/storage of the authentication (`X00x`) and encryption key (`E00x`) in the `IServerKeyStore`, subscriber transition `Initialized → Ready`, response as `ebicsKeyManagementResponse`, return codes (INI missing / already completed / broken order data), H003/H004 (`RSAKeyValue`) vs. H005 (X.509)
- [HPB — retrieval of the bank keys](server/hpb.md) — third order handler: return of the public **bank keys** (`X00x`/`E00x`) to a `Ready` subscriber via signed `ebicsNoPubKeyDigestsRequest`, response with **encrypted** `DataTransfer` (E002 hybrid for the subscriber, `HPBResponseOrderData` + `EncryptionPubKeyDigest`), a dedicated `IServerBankKeyStore` (auto-generated/seedable), return codes (subscriber not `Ready`/unknown), H003/H004 (`RSAKeyValue`) vs. H005 (X.509)
- [Key change & suspension (HCA/HCS/SPR/HSA)](server/hca-hcs-spr-hsa.md) — the final key-management handlers: **HCA/HCS** replace keys via signed `ebicsRequest` with **E002-encrypted** order data (decryption with the private bank key, purpose upsert in the `IServerKeyStore`, subscriber stays `Ready`), **SPR** sets the subscriber to `Suspended` (state machine), **HSA** as legacy HIA (H003/H004 only); response `ebicsResponse` (HCA/HCS/SPR) or `ebicsKeyManagementResponse` (HSA), return codes (`091002`/`090004`), spec caveat: no ES/X002 check (M4)
- [Segmentation, compression & Base64 pipeline](server/segmentation.md) — the cross-cutting byte pipeline of the transaction engine (M4): deterministic splitting of the compressed (possibly E002-encrypted) order-data byte stream into segments (`EbicsSegmentation.Split`/`Reassemble` in `EBICO.Core`) and configurable segment size (`EbicoServerOptions.SegmentSizeBytes`, raw bytes before Base64, default 512 KiB); builds on `EbicsCompression`, Base64 via `base64Binary` binding, edge cases (1 segment, empty OrderData); policy-free — transaction ID/phases/envelope & segment return codes wire up upload (#32)/download (#33)
- [Upload transaction (Initialisation + Transfer)](server/upload-transaction.md) — the first multi-phase transaction of the engine (M4): two-phase upload with **transaction-ID assignment** (Initialisation) and **segment-wise receipt** (Transfer) → reassembly/decryption (`EncryptionE002`)/decompression of the order data; a dedicated `UploadTransactionEngine` + in-memory `IUploadTransactionStore` (ADR-0013), phase routing in the pipeline, wired to **FUL** (H003/H004) / **BTU** (H005); transaction/segment return codes (`091101`/`091104`/`091103`/`011101`/`091114`); spec caveat: ES signature check of the OrderData deferred
- [Download transaction (Initialisation + Transfer + Receipt)](server/download-transaction.md) — the three-phase send transaction of the engine (M4): server-side **data provisioning** (`IDownloadDataProvider` + admin API, consuming) → compress/E002-encrypt (for the subscriber enc key)/**segment** (`EbicsSegmentation.Split`) → deliver `NumSegments`+segment 1 (init) and segments 2…N (transfer) → **receipt** (positive `011000` / negative `011001`, negative re-enqueues the data); a dedicated `DownloadTransactionEngine` + in-memory `IDownloadTransactionStore` (ADR-0014), upload/download routing via `OwnsTransaction`, wired to **FDL** (H003/H004) / **BTD** (H005); return codes (`090005`/`091101`/`091104`/`091112`/`091114`); spec caveat: unsigned response (X002 = M4)
- [Transaction recovery & timeouts](server/transaction-recovery.md) — the lifecycle closure of the transaction engine (M4): **idle timeout** per transaction (sliding `LastActivityAt` window, `IsExpired`/`Touch`), **eviction** of expired/orphaned transactions **lazily on access** (→ `091101`) **and** via the `TransactionCleanupService` (BackgroundService + `ITransactionEvictor`), **re-enqueue** of dequeued download data on expiry (exactly-once guard), **idempotency** of duplicate segments/init/receipt (retention = replay window, `091103`), upper bound of parallel transactions (`091115`); new `EbicoServerOptions` (`TransactionTimeout`/`TransactionCleanupInterval`/`MaxConcurrentTransactions`); spec caveat: no active recovery-sync flow (`061101` available, not triggered)
- [Event/protocol store (IEventLog)](server/event-log.md) — the shared **append-only** event store (M4, #69), from which **HAC** (M5) and the **Suite inspector** (M7) read as pure projections: an `EbicsEvent` model (customer/order/type/timestamp/`EbicsReturnCode`/**visibility** `CustomerVisible` vs. `Internal`/severity), the async, pluggable abstraction `IEventLog` (append + query) with a thread-safe in-memory default `InMemoryEventLog` (ring buffer `EbicoServerOptions.MaxEventLogEntries`), query filter `EbicsEventQuery` (customer/period/type/visibility/limit), **central** write point in the `EbicsRequestPipeline` (one event per request, covers key mgmt) + **lifecycle** events from the upload/download engine (Started/Completed/ReceiptNegative/Evicted); in-memory default pluggable for later SQLite (ADR-0011/ADR-0015); VEU events (`VeuPending`/`VeuSigned`/`VeuReleased`/`VeuCancelled`) since #42, see [VEU orders](server/veu-orders.md)

## Suite (Blazor UI)
